# 프로필: 시간 제한 과제 (해커톤, 실무형 코딩 평가)

`docs/process.md`에 더해 적용한다. 정해진 시간 안에 결과물을 내고, 작업 기록(대화, 터미널, git 로그)이 평가되는 환경을 가정한다.
아래 시간은 180분 기준이다. 시간이 다르면 비율대로 줄이거나 늘린다.

## 1. 시간표

| 시간 | 단계 (process.md) |
|---|---|
| 0:00~0:10 | ① 요구사항 읽기, 키트 복사, 첫 커밋 |
| 0:10~0:20 | ② 스펙 초안 + Open 질문 |
| 0:20~0:30 | ③④⑤ 질문 (최대 2라운드) → 결정 → `ready` → 커밋 |
| 0:30~2:20 | ⑥ 구현. Task 하나에 30분 이내 |
| 2:20~2:35 | ⑦ 검증, 교차 검증 1회 |
| 2:35~2:50 | ⑧ 마무리 |
| 2:50~3:00 | 제출 전 마지막 읽기 (4장), 제출 |

- 30분 이상 밀리면 범위를 줄이는 결정을 Decisions에 적는다.
- 에이전트 응답 시간을 계산에 넣는다. 에이전트가 일하는 동안 기다리지 말고, 다음 Task를 정리하거나 직전 결과의 숫자를 확인한다. 위임과 시간 안배도 평가된다.
- 터미널은 탭을 나눠 쓴다. 메인 에이전트 하나, 실행·테스트용 셸 하나, 교차 검증용 에이전트 하나.

## 2. 에이전트 추가 규칙

- 계획·리뷰·멀티 에이전트 같은 별도 스킬이나 플러그인 워크플로를 쓰지 않는다. 계획은 스펙의 Tasks, 검증은 process.md 8장이 전부다. 시간과 토큰을 아끼고, 평가 환경에 없는 도구에 기대지 않기 위해서다.
- 토큰 사용량도 평가될 수 있다. 같은 질문을 반복하지 않는다. 과제 설명은 다시 옮겨 적지 말고 파일 경로로 가리킨다.
- 컨텍스트 사용량이 절반을 넘으면 `docs/handoff.md`를 갱신하고 새 세션에서 이어간다. 70%를 넘기지 않는다.
- `git push`, 외부로 파일을 보내는 명령(업로드, 외부 API로 자료 전송)은 실행하지 않는다. 공개 자료를 가져오는 `git clone`·다운로드만 쓴다.
- 웹 서버는 `0.0.0.0`에 바인딩하고 실행 포트를 보고에 적는다 (`localhost`만 바인딩하면 플랫폼 미리보기에서 열리지 않을 수 있다). 서버를 띄운 터미널은 닫지 않는다.
- 컴퓨터 사용(Computer Use)·데스크톱 앱 조작·브라우저 자동 조작을 하지 않는다. 평가 환경에서 금지될 수 있다. 화면 확인이 필요하면 사람에게 요청한다.
- 메모리를 많이 쓰는 처리는 피한다. 큰 파일은 필요한 컬럼만 읽는다.
- 첫 커밋 메시지에 키트 출처를 적는다: `chore: 과제 자료와 작업 키트 추가 (github.com/kjhyeon0620/cofa-kit)`

## 3. 시작 전 점검 (사전 체험이 있으면 그때)

1. 공개 저장소 `git clone`이 되는가
2. 에이전트 실행, 모델·권한 확인, AGENTS.md를 읽는지 ("AGENTS.md 요약해줘")
3. `python3 --version`, `python3 -m pytest --version`, `bash scripts/check.sh`
4. 작업 공간이 처음부터 git 저장소인가 (`git status`)
5. 터미널 탭 나누기, 에디터 저장 상태, 웹 서버 미리보기

## 4. 제출과 사후 질의

- 제출을 확정하면 파일을 고칠 수 없는 경우가 많다. **확정 전에** 스펙의 알려진 격차와 Decisions를 다시 읽는다.
- 사후 질의(서술형, 인터뷰)는 AI 없이 직접 답한다고 가정한다. 문항은 제출물과 작업 기록으로 만들어진다.
- 질문의 전제가 실제 구현과 다르면 그 차이를 먼저 밝히고, 실제로 한 것을 설명한다.
- 문항당 시간이 짧다. 결론 한 줄 → 근거(파일·수치) → 약점·개선 순으로 쓰고 넘어간다.

## 5. 운영자 메시지 (사람이 에이전트에게 보내는 말)

`< >`는 바꿔 넣는다. 에디터에 이 파일을 열어 두고 쓴다.

**시작**
```text
AGENTS.md, docs/process.md, docs/profiles/timed.md를 읽어. 과제 설명은 <README 경로>에 있어.
키트와 과제 자료를 첫 커밋으로 남기고, 자료 품질을 코드로 확인한 뒤 docs/spec.md 초안과 요청자에게 물을 Open 질문을 최대 5개 뽑아줘. 질문은 현장 용어로 써.
```

**질문 답 전달**
```text
요청자 답변: <붙여넣기>
Decisions에 반영해. 모른다는 항목은 받은 자료로 확인하거나 기본값 가정으로 닫아. (2라운드째면: 남은 건 모두 닫고 ready로 바꿔.)
Tasks를 30분 이내 크기로 나누고 커밋 전에 보고해.
```

**Task 시작 / 승인**
```text
T<n> 진행해. 테스트 먼저. 끝나면 커밋 전 보고.
```
```text
승인. handoff 갱신해서 같이 커밋하고, 다음 Task 순서를 5줄로 보고한 뒤 바로 시작해.
```

**검증**
```text
docs/process.md 8장 검증을 해. 핵심 수치 3개를 원본에서 다른 경로로 재계산해 대조하고, 처리 방침별 민감도 표, 경계 상황 1개를 확인해서 완료 증거에 기록하고 커밋해.
그다음 새 세션에서 쓸 교차 검증 프롬프트를 출력해.
```

**마무리**
```text
마무리해(process.md 9장): README 실행 방법, 요약 1페이지, 요구사항 대조표, 알려진 격차와 회고, status: done, check.sh, 커밋.
그리고 내가 설명할 수 있어야 하는 결정 5개를 근거(파일·함수·수치)와 함께 출력해. 문서에는 쓰지 마.
```

**막혔을 때**
```text
범위를 넘었어. 스펙 범위 밖은 되돌리고 알려진 격차에 "범위 밖"으로 적어.
```
```text
같은 테스트가 3번 실패했어. 멈추고 원인 가설 2개와 각각 확인할 방법을 보고해. 기대값은 바꾸지 마.
```
```text
시간이 밀렸어. 남은 Task 중 요구사항 충족에 꼭 필요한 것만 남기고 나머지는 제외 범위로 옮긴 뒤 Decisions에 적어.
```
```text
스킬·플러그인·Computer Use는 쓰지 마(docs/profiles/timed.md 2장).
```
