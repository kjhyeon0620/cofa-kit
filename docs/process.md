# Spec-Driven 작업 절차 (시간 제한 과제용)

이 문서는 과제를 **스펙 → 구현 → 검증 → 회고** 순서로 진행하는 절차의 단일 기준이다.
사람과 AI가 같은 절차를 따른다. 기준 시간은 180분 과제다.

## 1. 원칙

- 구현 전에 **목적, 범위, 계약, 예외, 완료 증거**를 확정한다. 모호한 상태로 코드부터 쓰지 않는다.
- 대화 중에 내린 결정은 채팅에만 남기지 않고 `docs/spec.md`에 남긴다.
- "됐을 겁니다"로 끝내지 않는다. 완료 증거 표에 실행한 명령과 결과가 있어야 완료다.
- 절차의 무게는 남은 시간에 맞춘다. 문서는 한두 줄이면 충분하다. 절차를 지키느라 결과물을 못 내면 실패다.

## 2. 문서

| 문서 | 답하는 질문 |
|---|---|
| `AGENTS.md` | AI는 어떤 규칙으로 일하는가? |
| `docs/process.md` (이 문서) | 어떤 순서로 일하는가? |
| `docs/spec.md` | 이번 과제에서 무엇을, 어디까지 만들고, 어떻게 증명하는가? |
| `docs/handoff.md` | 지금 어디까지 왔고, 다음은 무엇인가? |
| `README.md` (결과물) | 사용자는 무엇을 받고, 어떻게 실행하는가? |

## 3. 진행 흐름

```text
① 과제 읽기 (0:00~0:10): 과제 설명과 자료 목록을 전부 읽는다. 아직 만들지 않는다
      ↓
② 스펙 초안 (0:10~0:20): AI가 과제와 자료를 읽고 docs/spec.md 초안을 쓴다
   데이터가 있으면 품질 점검 코드를 먼저 돌려 사실을 확인한다 (탐색은 ready 전에도 허용)
      ↓
③ 질문 (0:20~0:30): 구현자가 임의로 정해야 하는 것만 실무자에게 묻는다 (한 번에 최대 5개)
      ↓
④ 결정 기록: 답을 Decisions에 적는다. 제외 범위를 최소 2개 적는다
      ↓
⑤ ready: Open 질문이 0개가 되면 status: ready. 커밋 `docs(spec): ...`
      ↓
⑥ 구현 (0:30~2:20): status: in-progress. Task 단위로 테스트 먼저 → 구현 → 보고 → 승인 → 커밋
   가장 작은 끝-대-끝 버전(입력 → 처리 → 사용자가 보는 출력)을 먼저 완성한다
      ↓
⑦ 검증 (2:20~2:35): 완료 증거를 실행하고 결과를 적는다. 교차 검증 1회 (8장)
      ↓
⑧ 마무리 (2:35~2:50): 알려진 격차와 회고를 쓰고 status: done. 새 기능 금지 (9장)
      ↓
⑨ 서술형 대비 + 제출 (2:50~3:00): 제출 확정 전에 스펙을 다시 읽는다. 확정 후에는 파일을 수정할 수 없다
```

- 시간은 기준이다. 30분 이상 밀리면 범위를 줄이는 결정을 Decisions에 적는다.
- 에이전트 응답 시간을 계산에 넣는다. Codex가 일하는 동안 기다리지 말고, 다음 Task의 스펙을 쓰거나 직전 결과의 숫자를 확인한다. 응답 대기도 시간 안배 평가의 일부다.
- 터미널은 탭을 나눠 쓴다. 메인 `codex` 하나, 실행·테스트용 셸 하나, 교차 검증용 `codex` 하나.

### 상태값

| status | 의미 |
|---|---|
| `draft` | 작성 중이거나 Open 질문이 남아 있음 |
| `ready` | 결정이 끝나 구현을 시작할 수 있음 |
| `in-progress` | 구현 중 |
| `done` | 구현, 검증, 회고가 끝남 |

## 4. 질문 규칙

- 분량을 늘리기 위한 질문이 아니라 **아직 내리지 않은 결정**을 찾는 질문만 한다.
- 해법 단어(AI, 자동화, 대시보드)는 처음에 꺼내지 않는다. 현장 사실부터 묻는다.
- 코드나 자료를 읽으면 답이 나오는 것은 묻지 않고 직접 확인한다. 예: 중복 행이 완전히 같은 행인지, 값만 다른 재측정인지는 데이터로 확인한다.
- 실무자가 알 수 있는 것만 묻는다. 현장 용어로 묻고 컬럼명·기술 용어는 쓰지 않는다.
- 합리적인 기본값이 있으면 묻지 않고 "기본값 X로 가정"으로 Decisions에 적는다.
- **실무자가 "모른다", "확인해 봐야 한다"고 답한 항목은 Open으로 남기지 않는다.** 자료로 확인하거나, 기본값을 정해 Decisions에 `기본값 X로 가정 (실무자 미확인)`으로 적고, 알려진 격차에 "확인되면 바꿀 곳"을 적은 뒤 진행한다. 시험 안에서 답이 오지 않는 질문을 기다리면 구현을 시작할 수 없다.
- 질문은 최대 2라운드다. 2라운드 뒤에도 남은 항목은 위 방식으로 닫고 `status: ready`로 바꾼다.

### 실무자에게 먼저 확인할 것

- 지금 겪는 구체적 사례 하나 (언제, 무엇이, 얼마나)
- 지금은 어떻게 버티고 있나 (워크어라운드)와 그 비용 (시간, 빈도)
- 결과물을 누가, 어디서, 언제 쓰나. 그 사람의 환경 제약 (설치 가능 여부, 비개발자인지)
- 성공 기준을 숫자로 (지금 값 → 목표 값, 측정 방법)
- 이번에 하지 않아도 되는 것

### 과제 유형별로 특히 확인할 것

| 유형 | 확인할 것 |
|---|---|
| 데이터 분석 | 중복 행, 결측, 단위 혼재, 값 범위 이상, 날짜 범위. **기준·규칙의 적용 시작일과 버전**. 원인처럼 보이는 그룹이 다른 변수와 겹치는지 (교란 요인) |
| 기능 구현 | 입력 검증 경계, 같은 요청이 두 번 오면, 외부 의존이 실패하면, 데이터가 없으면 사용자가 무엇을 보나 |
| 버그 수정 | 재현 명령, 기대값과 실제값, 언제부터 그랬나 |
| 자동화·LLM 활용 | 무엇을 코드로 판정하고 무엇을 LLM이 해석하나, 틀렸을 때 사람이 어떻게 알아채나, 비용 |

## 5. 구현 재량과 범위 변경

| 구현 재량 (AI가 결정) | 범위 변경 (스펙을 고친 뒤 진행) |
|---|---|
| 내부 함수 구조, 이름 | 새 출력물, 새 화면, 새 입력 |
| 계약 안에서의 리팩토링 | 출력 형식·필드, 판정 기준 변경 |
| 테스트 헬퍼 추가 | 새 외부 의존성 |
| 로그 문구 | 제외 범위 해제 |

### 구현 중 스펙 변경

| 변경 종류 | 처리 |
|---|---|
| 사실 정정(자료가 스펙의 전제와 다름), 구현 재량 안의 결정, 새로 발견한 예외, 완료 증거 보강 | **스펙을 바로 고치고 계속한다.** Decisions에 `HH:MM (구현 중) 내용 → 결정. (이유)`로 남긴다 |
| 범위 변경 (위 표의 오른쪽 열) | **스펙 수정안을 쓰고 Open 질문으로 올린 뒤 묻고 기다린다.** 기다리는 동안 영향 없는 부분은 계속한다 |
| 범위 밖에서 발견한 결함·개선 | 알려진 격차에 "범위 밖"으로 적는다 |

- 뒤집힌 결정은 지우지 않고 "→ HH:MM 변경"으로 남긴다. 판단이 바뀐 과정도 평가 대상이다.

## 6. 유형별 구현 순서

### 데이터 분석
1. 품질 점검을 **코드로** 돌린다 (행 수, 고유 키 중복, 결측, 값 범위·단위, 날짜 범위). 결과를 완료 증거에 적는다.
2. 품질 문제마다 처리 방침(제거, 보류, 보정)과 처리한 행 수를 Decisions에 적는다.
3. 판정 로직을 순수 함수로 만들고 테스트를 먼저 쓴다 (경계값, 결측, 기준 변경일 전후).
4. 원인 후보를 나열하고 후보마다 비교한다 (전/후, 그룹 간). 한 변수만 보고 결론 내지 않는다.
5. 원인처럼 보이는 그룹을 다른 변수와 교차표로 확인한다. 겹치면 그 변수를 고정하고 다시 비교한다.

### 기능 구현
1. 이미 있는 코드와 자료를 재사용한다. 데이터 형태를 먼저 정한다.
2. 핵심 로직 테스트 → 가장 작은 끝-대-끝 버전 → 실제 실행.
3. 실행 방법을 한 줄 명령으로 README에 적는다. 다듬기는 검증과 문서가 끝난 뒤다.

### 버그 수정
1. 재현한다. 재현 못 하면 고치지 않는다.
2. 실패하는 테스트를 먼저 커밋한다.
3. 원인 지점만 고친다. 같은 재현 명령으로 다시 확인한다.

## 7. Tasks 쓰는 법

구현을 Task로 나눠 AI에게 하나씩 맡긴다. Task마다 아래 네 줄을 쓴다.

```
### T1. <이름>
- 먼저 읽을 것: (파일, 함수, 스펙 섹션)
- 변경: (만들거나 고칠 것)
- 금지: (이 Task에서 건드리지 않을 것)
- 검증: (실행할 명령과 기대 결과)
```

Task는 30분 안에 끝나는 크기로 자른다. 한 Task가 끝나면 보고 → 승인 → 커밋 → `docs/handoff.md` 갱신.

## 8. 검증

- 완료 증거 표의 모든 행을 실행하고 **결과 칸에 실제 수치**를 적는다. 결과 칸이 빈 행은 증명하지 않은 것이다.
- 테스트 통과만으로 끝내지 않는다. 사용자가 쓰는 방식 그대로(README의 명령) 실행하고 출력을 열어 본다.
- 출력의 숫자 3개 이상을 원본 자료와 직접 대조한다.
- 경계 상황 하나를 일부러 넣어 본다 (빈 값, 없는 날짜, 잘못된 입력).
- 결과에는 환경을 적는다 (샘플 데이터 / 전체 데이터 / 수동 확인). 일부만 확인한 것을 전체 검증으로 표현하지 않는다.

### 교차 검증 (1회)

새 터미널 탭에서 `codex`를 새로 열고 `docs/spec.md`, 핵심 코드, 결과물을 읽게 한 뒤 아래 형식으로 판정하게 한다. 메인 세션의 결과를 같은 세션이 판정하지 않게 하기 위해서다.

```text
아래 형식으로 판정해라. 칭찬은 생략한다.
- recommendation: APPROVE / REQUEST_CHANGES
- 원래 의도: (스펙의 목적과 성공 기준을 한두 문장으로)
- 결과 판정: 성공 기준을 충족하는가. 근거가 되는 파일·함수·수치
- 틀렸거나 근거가 약한 곳: (위치, 이유)
- 확인한 파일
- 증거 공백: 실행하지 않아 판정할 수 없는 것
```

지적을 반영하거나, 반영하지 않으면 이유를 Decisions에 적는다.

## 9. 마무리, 제출, 서술형 대비

종료 25분 전에 시작한다. 새 기능은 만들지 않는다.

1. `bash scripts/check.sh` 통과
2. 과제가 지정한 제출물과 파일명을 다시 확인한다. 과제 안내가 이 키트보다 우선이다.
3. README: 무엇을 만들었나, 실행 방법(한 줄), 결과물 위치, 한계
4. 비개발자용 요약 1페이지: 결론 → 근거 수치 → 권고 조치 → 한계
5. 스펙의 **알려진 격차**와 **회고**를 채우고 `status: done`
6. 최종 커밋 `docs: 제출 정리`. 에디터 저장 상태와 저장 충돌 표시를 확인한다.
7. **제출 확정 전에** 알려진 격차와 Decisions를 다시 읽는다. 확정한 뒤에는 파일을 수정할 수 없고, 서술형 중에는 AI도, 복사·붙여넣기도 쓸 수 없다. 항목마다 3단계로 말할 수 있는지 확인한다.
   1. 약점 지점을 구체적으로 지목 (파일, 함수, 수치)
   2. 왜 위험한지, 어디로 번지는지
   3. 무엇을 검증·개선할지
8. 종료 10분 전까지 "제출하고 문제풀기" → 미리보기 확인 → "제출물 확정하고 문제풀기"

### 서술형 (문항당 5분, 이전 문항으로 돌아갈 수 없음)
- 문항은 제출물과 작업 기록(대화, 터미널, git 로그)으로 만든다. 직접 결정한 이유를 내 말로 설명할 수 있어야 한다.
- 질문의 전제가 실제 구현과 다르면 그 차이를 먼저 밝히고, 내가 실제로 한 것을 설명한다.
- 5분은 짧다. 결론 한 줄 → 근거(파일·수치) → 약점·개선 순으로 쓰고 다음 문항으로 넘어간다.

## 10. 회고

| 원인 | 다음에 고칠 위치 |
|---|---|
| 동작을 정해 두지 않았음 | 스펙 질문 항목 (4장) |
| 규칙은 있었지만 AI에게 전달되지 않았음 | `AGENTS.md` |
| 틀렸는데 검사하지 않았음 | 테스트, `scripts/check.sh` |
| 완료 판단이 느슨했음 | 스펙의 완료 증거 |

- "앞으로 주의한다"보다 **테스트나 검사 스크립트로 바꾸는 것**을 먼저 검토한다.
